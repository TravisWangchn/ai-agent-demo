Agent 架构

一个工单，五个阶段，七层轨迹

Agent 的工作不是“收到请求就直接改代码”。它先确认请求来自哪里、是否被规则授权，再判断信息是否足够，最后才进入执行与交付。五阶段回答“系统怎么工作”，七层执行轨迹回答“这一次到底发生了什么”；两者叠加，才能既不丢全局结构，又能逐步复盘。

五阶段工作流

每个阶段都有明确的输入、判断与产物

  1. STEP 01

    触发

    Issue、评论或消息进入系统，记录原始来源与请求文本。

    →
  2. STEP 02

    评估

    读取有限的相关上下文，匹配策略规则，确认范围与前提。

    →
  3. STEP 03

    决策

    依据接受条件判断：接受、要求补充、忽略还是停止。

    →
  4. STEP 04

    执行

    在独立分支完成局部改动，补测试与文档，并进行自检。

    →
  5. STEP 05

    交付

    提交可审阅的 PR，附验证方式与必要证据，等待评审。

每个阶段在做什么

关键在于：前三个阶段只读，后两个阶段才产生改动

  1. 01

    触发：先确认“谁在什么场景下提出了什么”

    请求可能来自 GitHub Issue、PR 评论、聊天消息或定时任务。Agent 记录来源、原始文本和上下文指针，但不会把“收到请求”当成“获得任意改动授权”。来源本身只决定如何回复，不决定可以改什么。

    输入：Issue / 评论 / 消息 产物：触发记录
  2. 02

    评估：只读上下文，不做修改

    Agent 收集完成判断所需的最小上下文：仓库约定、涉及文件、历史决策和请求中已确定的信息。随后匹配策略规则，确认任务属于哪一类、授权边界在哪里、是否缺少必要前提。评估阶段不写文件，也不提前开始实现。

    输入：请求 + 仓库上下文 产物：规则匹配与范围判断
  3. 03

    决策：说明依据，而不是只说结论

    决策可能是接受、要求补充信息、忽略或停止。每个结论都要能回答“依据哪条规则、为什么”。如果请求缺少可执行的前提，正确动作是退回补充，而不是替请求人选择设计方向。

    输入：规则 + 接受条件 产物：决策与理由
  4. 04

    执行：小步改动，随时可验证

    在独立分支完成局部修改，同时补齐测试、文档和必要的验证脚本。执行中如果发现需要改变公共接口、模块职责或产品方向，应暂停并上报；不能把“实现方便”当成扩大范围的授权。

    输入：已接受的规格 产物：代码、测试、自检结果
  5. 05

    交付：把判断变成可复核的证据

    交付物是一个可审阅的 PR：改了什么、为什么改、如何验证，以及用户能观察到的结果。视觉变化附 Before/After 截图。CI 与人类评审负责最终把关，Agent 不绕过评审，也不自行合并。

    输入：可运行的改动 产物：PR + 验证证据

执行轨迹如何进入架构

轨迹不是另起一套流程，而是把五阶段中每个节点的输入、输出与判断留痕

五阶段描述的是系统的职责分层；七层轨迹描述的是某一次工单实际发生了什么。一个阶段可能产生多条轨迹步骤（例如执行阶段同时产生 tool_call 与 tool_result），一条轨迹步骤也能对应回某个阶段（例如 reasoning 对应评估与决策）。把两者叠在一起，读者既能看懂全局结构，也能沿着时间线逐步复盘。

DSH Super-Agent 调用链路

从外部事件到可交付汇总，六个节点依次推进

  1. 01

    触发：外部事件进入编排入口

    GitHub Issue 的 opened 事件被接收，记录仓库、编号、提交者、时间戳与原始正文。此时不修改任何文件，也不把“收到工单”当成改动授权。对应轨迹层 trigger（source: event），承接角色是 github。

    轨迹层：trigger 角色：github
  2. 02

    orchestrator 评估与规则匹配

    编排器读取最小必要上下文，按策略规则逐项检查接受条件，得到“接受 / 要求补充 / 忽略 / 停止”的结论，并说明依据。对应轨迹层 reasoning（source: agent）。

    轨迹层：reasoning 角色：orchestrator
  3. 03

    plan：拆成带依赖的子任务

    把工单拆成带依赖顺序与所属工具的子任务序列（标准轨迹拆成 7 个子任务：P1 确认基线（git）→ P2 读取契约与现有实现（filesystem）→ P3 实现轨迹数据与回放模块（filesystem）→ P4 实现轨迹页面与样式（filesystem）→ P5 编写使用文档与 README（filesystem）→ P6 生成标准快照并接入 CI（shell）→ P7 提交分支、创建 PR 并校验 CI（github））。依赖关系必须可判定，不能成环。对应轨迹层 plan。

    轨迹层：plan 角色：orchestrator
  4. 04

    worker 工具调用与原始返回

    按子任务向真实工具下发指令：git、filesystem、shell、node:test、github。指令原文与参数记录在 tool_call，退出码、耗时与关键输出记录在 tool_result；失败结果同样保留，供复盘。

    轨迹层：tool_call / tool_result 角色：worker + 工具
  5. 05

    分支与异常处置

    依据退出码、测试结果与规则决定下一步：正常推进，或进入异常分支并记录来源节点、目标节点、异常类型与处置方式。异常分支不得通过放宽断言绕过。对应轨迹层 branch。

    轨迹层：branch 角色：orchestrator
  6. 06

    summary：汇总产出并交接

    编排器汇总整条轨迹的结论，列出产出物清单与后续动作（例如提交分支、触发 CI 快照校验、等待评审）。对应轨迹层 summary，是闭环交付的最后一层。

    轨迹层：summary 角色：orchestrator

工具与能力依赖关系

工具名与命令都来自本仓库真实可复现的操作，不虚构插件或 API

架构节点由哪些真实工具承接，以及它们在轨迹里留下哪类证据。
工具 / 能力 真实形态 承接的架构节点 典型轨迹层
github gh CLI：读取 Issue、创建 / 更新 PR 触发、交付 trigger / summary
filesystem read / write / edit 文件工具 评估、执行 tool_call / tool_result
shell pwsh / 命令行：npm test、npm run snapshots、node scripts/… 执行、验证 tool_call / tool_result
node:test Node 内置测试运行器（node --test） 自检与验收 tool_result
git git CLI：fetch / checkout / diff 基线确认与分支 tool_call / tool_result
orchestrator DSH Super-Agent 编排器 评估、拆解、分支、汇总 reasoning / plan / branch / summary
worker 执行子任务的 Agent 角色 实现与自检 reasoning

七层轨迹与架构节点映射

同一份数据既驱动页面回放，也驱动快照与测试断言

七层轨迹的定义与它们在架构中对应的节点、留下的典型证据。
层级（id） 中文名 来源 对应架构节点 典型证据
trigger 工单原始输入 event 触发 Issue 元信息与正文
plan 任务拆解规划 agent 决策 → 执行 子任务、依赖、所属工具
tool_call 工具调用请求 tool 执行 命令、cwd、文件路径参数
tool_result 工具返回 Payload tool 执行、自检 退出码、耗时、输出摘录
reasoning Agent 决策推理 agent 评估、决策 命中规则、判定结论、依据
branch 分支跳转 agent 决策 → 执行 正常 / 异常、from/to、处置方式
summary 最终汇总输出 agent 交付 产出物清单、后续动作

贯穿全流程的三条原则

规则先于动作

先匹配规则、确认授权边界，再决定是否执行。没有明确规则时，默认不扩大范围。

证据先于声明

测试输出、可复现步骤和截图，比一句“已完成”更有价值。结论必须能被独立复核。

人类保留最终决定

合并、发布和方向选择由人负责。Agent 可以准备充分材料，但不能替人做最终判断。
